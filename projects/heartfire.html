Case study / Software

Heartfire

A terminal-based dark fantasy dungeon crawler written in C++, built to practice program structure and object-oriented programming on something larger than a single-file exercise.

status
In development. A personal project, not a commercial release.
role
Solo developer, handling design and implementation
tech
C++, object-oriented programming, Visual Studio, Git, ANSI escape codes, ASCII and Unicode art

Overview

Heartfire is a dungeon crawler that runs entirely in a terminal window. The player creates a character, works through a hub area, then descends through floors of a dungeon, fighting enemies, managing an inventory, and searching rooms for the keys and treasure needed to keep going. Locations include Tradefall, The Weeping Willow, and the Wyrmheart Depths, ending at a final dragon encounter.

It is a learning project. I picked a game because a game forces problems a small exercise never does: state that has to persist between turns, entities that need to share behavior, and a program too large to keep in one file.

Goal

Coursework exercises are usually one file and a few dozen lines. I wanted to find out what happens after that, when a program stops fitting in your head and organization starts to matter more than syntax. Heartfire is the project I use to run into those problems on purpose.

What I built

  • Character creation at the start of a run
  • Menu-driven navigation and input handling throughout
  • Turn-based combat against enemies
  • An inventory system for items the player finds
  • Rooms to explore, with treasure and keys gating progress
  • Multiple dungeon floors to descend through
  • A final dragon encounter
  • A terminal interface drawn with ASCII and Unicode art, colored with ANSI escape codes

Core gameplay loop

  1. Explore a room
  2. Fight whatever is in it
  3. Search for treasure and keys
  4. Find the way forward
  5. Descend
  6. Repeat

Technical concepts practiced

  • Multi-file organization: splitting the program across headers and source files instead of one long main()
  • Classes and objects: modeling the player, enemies, items, and rooms as types with their own data and behavior
  • Collections: holding groups of things, such as an inventory or the enemies in a room
  • Game state: tracking what persists between turns, floors, and encounters
  • Menu-driven input: reading player choices and handling input that isn't valid
  • Terminal presentation: ANSI escape codes for color, ASCII and Unicode for layout
  • Debugging: stepping through logic in Visual Studio to find where state goes wrong
  • Version control: Git for history and for keeping work-in-progress separate

Where it's going next

  • More content: additional floors, enemies, and items
  • Saving and loading a run in progress
  • Tightening the combat balance so encounters stay interesting
  • Continuing to refactor as the program grows, keeping files focused on one job
